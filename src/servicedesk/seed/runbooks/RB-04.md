# RB-04 Checkout latency investigation

The checkout path is `lb-01` (load balancer) to `web-checkout-01` and `web-checkout-02`, then `app-checkout-01`, which uses the session cache `cache-02` and the orders database `db-04`. The standby database `db-05` receives replication from `db-04`.

## Targets

- Order confirmation p95 latency: under 2 seconds.
- Page errors with code `CHK-TIMEOUT-504`: fewer than 1 in 1,000 requests.

## Step 1: find the slow layer

1. Check the `lb-01` pool. If one web server is marked down, the other carries all traffic and slows down.
2. Compare response times of `web-checkout-01` and `web-checkout-02`. A difference points to one server.
3. Check the thread pool on `app-checkout-01`. More than 90% busy means it is waiting on something downstream.

## Step 2: check the cache

1. The `cache-02` hit rate should be above 85%.
2. A low hit rate and high evictions mean the cache is too small (see INC-0020 and CHG-0002).

## Step 3: check the database

1. Open the slow query log on `db-04`. Queries over 1 second during the day are not normal.
2. Check CPU and the disk queue of the `db-04` volume on `san-01`.
3. Check replication lag to `db-05`. Alert `ERR-REPL-LAG` fires above 300 seconds.
4. Reporting jobs from other services (for example `crm-nightly-report`) must not run on `db-04` during business hours. Stop them if they do.

## Step 4: decide

- If the database is the bottleneck and the lag is under 30 seconds, consider a failover to `db-05` (RB-06). A failover is a change: it needs an approved change request (RB-05).
- Remember that the CRM also uses `db-04`. Any database action affects both checkout and CRM.
